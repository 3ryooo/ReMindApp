# Re:Mind ランダムリマインダー 

## 概要

このアプリは、ユーザーが登録した言葉やフレーズを、設定した時間にランダムに通知することで、日々のモチベーション維持や大切なことの再認識をサポートすることを目的としたiOS向けアプリケーションです。

[App Storeで見る](https://apps.apple.com/jp/app/remindapp/id6752647254)

## 主な機能

- リマインダーの登録・編集・削除
- リマインダーごとの通知ON/OFF
- 登録した言葉のリスト表示
- 登録日時または名前による並び替え
- 複数選択による一括削除
- 基準時刻と通知間隔の設定
- 通知する言葉のランダム選択
- 1日以上の通知間隔における通知時刻のランダム化
- 通知権限が無効な場合の設定画面への案内
- iCloudを利用したデータ同期

## 設計

画面、状態・ロジック、データモデルの責務を分離しています。

```text
ReMindApp/
├── Sources/
│   ├── Screens/       # 各画面
│   ├── Views/         # 再利用するView
│   ├── View Modifiers/
│   ├── Models/        # SwiftDataモデル
│   ├── Stores/        # 状態管理・アプリケーションロジック
│   ├── Protocols/     # 外部依存の抽象化
│   ├── Utils/
│   └── Custom Errors/
└── Tests/
    ├── UnitTests/
    ├── IntegrationTests/
    └── UITests/
```

`ReminderStore`がリマインダーの操作と並び替えを、`NotificationStore`が通知設定の保存と通知予約を担当します。

通知スケジューラー、時刻取得、UserDefaultsへのアクセスをProtocolで抽象化し、実際のOS機能に依存せずロジックをテストできる構成にしています。


## テスト

Swift Testingを使用し、主に次の項目を検証しています。

- リマインダーの保存・削除・並び替え
- 入力文字列のバリデーション
- UserDefaultsへの通知設定の保存
- 通知ON/OFF時の予約・削除処理
- 最大64件の通知予約
- ランダムな通知内容の選択
- 基準時刻と通知間隔からの通知日時計算
- 通知予約失敗時のエラー処理
- SwiftDataと通知処理を組み合わせた一連のフロー

XCTestではアプリの起動と起動パフォーマンスを検証しています。

テストダブルは、テストフレームワークの都合ではなく、OS機能や永続データなどの外部依存を制御する目的で使用しています。現在は次のMockを用意しています。

- `MockNotificationScheduler`：実際の通知を登録せず、予約内容と呼び出し回数を検証
- `MockUserDefaults`：実際のUserDefaultsを変更せず、設定の保存・読み込みを検証
- `MockTimeProvider`：現在時刻を固定し、通知日時の計算を再現可能にする

## 学習と開発プロセス

SwiftUIの基礎は、実際に手を動かして課題へ取り組む[100 Days of SwiftUI](https://www.hackingwithswift.com/100/swiftui)を中心に学習しました。そのうえで、アプリに必要なデータ永続化、ローカル通知、テスト、アーキテクチャについて個別に調査し、採用する技術を判断しています。

テストについては、[Testing Swift](https://www.hackingwithswift.com/store/testing-swift)などを参考に、テストの種類と対象を分けて設計しました。ビジネスロジックとデータ処理のユニット・統合テストにはSwift Testingを、アプリの起動と起動パフォーマンスの検証にはXCTestを使用しています。ユーザー操作を検証するUIテストは今後拡充する予定です。

## 技術選定と判断

### データ永続化：Core DataではなくSwiftDataを採用

データ永続化には、Core DataとSwiftDataの両方を候補として検討しました。

本アプリで扱うデータは、文字列、通知ON/OFF、登録日時を持つ比較的単純なリマインダーモデルが中心です。また、対応OSをiOS 18.0以降としているため、古いOSとの互換性を目的にCore Dataを選択する必要もありませんでした。

この条件では、SwiftUIとの統合が容易で、モデル定義やデータ取得を簡潔に記述できるSwiftDataの方が、実装・保守コストに対して得られる効果が大きいと判断しました。

### アーキテクチャ：MVVMではなくStoreパターンを採用

当初はMVVMの採用を検討しましたが、SwiftUI・SwiftDataにおける状態管理と責務分離を調査し、現在はStoreパターンを採用しています。

[Mastering SwiftUI Architecture: Patterns and Best Practices](https://www.udemy.com/course/mastering-swiftui-architecture-patterns-and-best-practices/)などを参考に、画面ごとにViewModelを追加する構成と、機能単位で状態とロジックをまとめるStore構成を比較しました。

本アプリでは、SwiftDataの`ModelContext`と`@Query`をViewから利用しつつ、並び替えや通知予約などのアプリケーションロジックをStoreへ分離しています。小規模なアプリに多数のViewModelを設けるよりも、次の責務で分割する方が構造を把握しやすく、テストもしやすいと判断しました。

- View：画面表示、入力、SwiftDataとの接続
- `ReminderStore`：リマインダーの操作と並び替え
- `NotificationStore`：通知設定、日時計算、通知予約
- Model：永続化するデータと入力検証

## 技術的に工夫した点

### 1. ローカル通知の上限を考慮した通知予約

iOSで保留できるローカル通知数を考慮し、最大64件の通知を事前に予約しています。

通知の設定を保存するたびに既存の予約を更新し、通知間隔、基準時刻、ランダム設定を反映します。最後の通知では上限に達したことをユーザーへ案内し、通知が途切れた理由を把握できるようにしています。

### 2. 通知内容と時刻のランダム化

通知対象がONになっているリマインダーから、通知ごとに表示内容をランダムに選択します。

また、通知間隔が1日以上の場合は時刻もランダムにできるようにし、決まった時間の通知に慣れて読み飛ばしてしまうことを防ぐ設計にしています。

### 3. テストしやすい依存関係

`UNUserNotificationCenter`、`UserDefaults`、現在時刻への直接依存を避けるため、次のProtocolを定義しています。

- `NotificationScheduling`
- `UserDefaultsProtocol`
- `TimeProvider`

テスト時にはMockへ差し替えることで、通知予約の回数、保存値、日時計算、エラー発生時の挙動を再現可能にしています。

SwiftDataを利用するテストでは、永続ストアへ書き込まないインメモリの`ModelContainer`を使用しています。これにより、開発・本番用データを変更せず、テストごとに独立した状態で検証できます。

### 4. 入力検証とエラーハンドリング

空文字・空白のみの入力や200文字を超える入力を検証し、ユーザーへ原因を表示します。

通知予約の一部が失敗した場合も、失敗件数を含むエラーメッセージを表示し、処理の失敗を見逃さないようにしています。

### 5. 設定変更の安全な取り扱い

設定画面では編集内容を一時的な状態として保持し、「保存」を選択した場合のみ通知設定へ反映します。未保存の変更がある状態で閉じようとした場合は、破棄してよいか確認します。
